# MAIL-Bench

**MAIL-Bench: Benchmarking Robotic Manipulation under Visual Availability Interruptions and Loss**

MAIL-Bench measures how an embodied manipulation policy behaves when one or
more cameras become unavailable partway through a task: can it still finish, at
what phase of the task does it start to fail, and how does its completion
efficiency change. It evaluates one fixed multi-task policy on RoboCasa
Atomic-Seen (18 tasks x 50 frozen scenes), with vision lost at 30 %, 45 % or
60 % of the policy's own healthy completion step in one of three visual roles
(wrist, agentview, all vision). Any model design and training method are
allowed. The protocol, the scoring rule and the validity conditions are in
[`docs/MAIL_BENCH_PROTOCOL.md`](docs/MAIL_BENCH_PROTOCOL.md).

## Reference results

| Policy | Reported | H | Wrist .30/.45/.60 | Agentview .30/.45/.60 | All vision .30/.45/.60 | S_MAIL |
| --- | --- | --- | --- | --- | --- | --- |
| pi0.5 (RoboCasa multitask) | 0.396 | 0.402 | 0.165 / 0.219 / 0.307 | 0.340 / 0.365 / 0.476 | 0.038 / 0.086 / 0.176 | **0.257** |
| GR00T N1.5 (RoboCasa365 official) | 0.507 | 0.450 | 0.165 / 0.267 / 0.377 | 0.247 / 0.285 / 0.407 | 0.048 / 0.089 / 0.124 | **0.246** |

"Reported" is the Atomic-Seen success each checkpoint's publisher reports under
their own protocol. The records are in `results/`; the table is generated by

```bash
python scripts/paper_results_table.py \
  --record pi0.5=results/mail_bench_pi05_score.json --reported pi0.5=0.396 \
  --record GR00T=results/mail_bench_groot15_score.json --reported GR00T=0.507
```

The two reference servers, `scripts/pi05_robocasa_policy_server.py` (openpi +
JAX, port 7606) and `scripts/groot15_robocasa_policy_server.py` (torch, port
7614), are complete examples of the policy contract.

## Installing

```bash
git clone https://github.com/minglejiang/MAIL-Bench.git && cd MAIL-Bench
pip install -e ".[all]"
pytest
```

Running a cohort also needs RoboCasa365 at the revision pinned in
`configs/dataset_registry.yaml`, its MuJoCo renderer with EGL, a GPU for the
policy server and `zstd`. The benchmark runs from a git checkout: every run
records the checkout's commit and refuses a dirty worktree, so keep the virtual
environment outside the checkout or name it `.venv/`.

## Running the official pipeline

```bash
# 1. Unpack the frozen scene bank that ships with the repository (once)
zstd -d -c scene_bank/mail_bench_scene_bank_official.tar.zst | tar -x -C <data dir>

# 2. Healthy: one canonical rollout per scene
python scripts/run_robocasa_cohort.py --scene-bank <data dir> --official --phase healthy \
  --policy custom --policy-port <port> --model-id <id> --model-revision <commit> \
  --inventory-sha256 <digest> --output-dir <out>

# 3. Completeness -> H per task, completion-step distribution
python scripts/report_healthy_phase.py --run-root <out>

# 4. This policy's own onset manifest
python scripts/build_onset_manifest.py --run-root <out> --model-id <id> --out <manifest.json>

# 5. The nine fault conditions, on healthy-solved scenes only
python scripts/run_robocasa_cohort.py --scene-bank <data dir> --official --phase fault \
  --policy custom --policy-port <port> --model-id <id> --model-revision <commit> \
  --inventory-sha256 <digest> --output-dir <out>

# 6. Ten-condition task scores -> the 18-task MAIL-Bench score
python scripts/report_mail_bench_score.py --run-root <out>
```

`--phase all` runs steps 2 and 5 in one invocation; several workers shard with
`--workers N --worker-index i`. `--official` verifies the scene bank, the suite
and the pinned weights before any rollout, and the scorer refuses the
benchmark's name unless every condition in protocol §6 holds. Anything else is
an experiment: `--allow-experiment` prints its record under the neutral name
`score`.

## Mechanism analyses

Optional studies outside the ranking (never `--official`; the healthy phase and
the onset manifest are shared with the ranking run):

```bash
# Failure Form at the 60 % onset: blackout, freeze, stale_k (500 ms delay) or burst_dropout (500 ms blocks)
python scripts/run_robocasa_cohort.py --scene-bank <data dir> --phase fault --onsets 0.60 --fault-mode blackout --output-dir <out>/blackout ...

# Missing Duration: the loss ends at 0.25 / 0.50 of the remaining episode (1.00 is the ranking cell)
python scripts/run_robocasa_cohort.py --scene-bank <data dir> --phase fault --onsets 0.45 --duration-fraction 0.25 --output-dir <out>/dur025 ...

# Visual Recovery: lost at 30 %, back at 60 % of the healthy completion step
python scripts/run_robocasa_cohort.py --scene-bank <data dir> --phase fault --onsets 0.30 --recovery-fraction 0.60 --output-dir <out>/recovery ...

# Score any of them
python scripts/report_mail_bench_score.py --run-root <out>/blackout --allow-experiment
```

Durations are given in milliseconds (`--stale-ms`, `--burst-ms`) and resolved
at the platform's control rate.

## Submitting your own policy

Implement a socket server that speaks `mcr-policy-v1` (`health`, `identity`,
`reset`, `act`, `disconnect`; a server declaring `stateful_policy: true` also
receives `invalidate` and `visual_memory_reset`), start it, and run the
pipeline above with `--policy custom --policy-port <port>`. The two reference
servers are complete examples; the required `identity` fields are listed in
`src/mail_bench/policy_api/contract.py`. Before spending the compute, let the
preflight tell you what an official run would stop on:

```bash
python scripts/check_submission.py --policy-port <port> --model-revision <commit> --inventory-sha256 <digest>
# optional: the same server started a second time on another port, to check that two processes agree
python scripts/check_submission.py --policy-port <port> --second-port <port2> --model-revision <commit> --inventory-sha256 <digest>
```

`<digest>` is the `inventory_sha256` of the weights the server loads, computed by

```bash
mail-inventory --root <checkpoint dir> --dataset-id <id> --revision <commit> --accessed-on <YYYY-MM-DD> --output inventory.json
```

## Repository layout

- `docs/MAIL_BENCH_PROTOCOL.md`: the protocol; `configs/perturbation_protocol.yaml` is its machine-readable form.
- `configs/`: the frozen suite, the reference roster, the platform profile, the pinned RoboCasa365 revision and the identity of every frozen scene.
- `data_inventory/`: the digest inventory of the pinned RoboCasa365 asset tree.
- `scene_bank/`: the 900 frozen scenes, compressed, with their checksum.
- `src/mail_bench/`: the execution kernel, the simulator adapter, the socket contract and the scorer.
- `scripts/`: scene bank construction, cohort execution, reports, the submission preflight, the results table and the two reference servers.
- `results/`: the two reference runs' score records, healthy reports and checkpoint receipts.
